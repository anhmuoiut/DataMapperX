## Implemented statistical model

### Normal process capability

The user chooses the within-sigma estimator explicitly. For individual observations in input order, `MR_i = abs(x_i - x_(i-1))` and `sigma_within = mean(MR_i) / 1.128` (moving range length 2). For identified rational subgroups, `d = sum(n_i - 1)`, `S_p = sqrt(sum((x_ij - mean_i)^2) / d)`, and the bias-corrected estimate is `S_p / c4(d + 1)`. The correction can be disabled. The overall estimate is the sample standard deviation across all observations, with denominator `N - 1`. The supported choices follow Minitab's [Normal Capability Analysis estimation methods](https://support.minitab.com/en-us/minitab/help-and-how-to/quality-and-process-improvement/capability-analysis/how-to/capability-analysis/normal-capability-analysis/methods-and-formulas/methods/).

`Cp = (USL - LSL) / (6 * sigma_within)` and `Cpk` is the smaller of the available upper and lower distances from the mean divided by `3 * sigma_within`. `Pp` and `Ppk` use the overall estimate instead. Cp/Pp require both limits; one-sided Cpk/Ppk use the available side. Zero denominators produce N/A rather than infinity. The acceptance decision is based on the unrounded Cpk, strictly greater than the configured threshold (default 1.33).

Repeated measurements of one serial number are suitable part groups for a measurement-system study. They are **not automatically rational subgroups for process capability**: the user must select a subgroup field that represents the actual sampling design. Moving-range estimates depend on the observation order. A capability result does not establish process stability, independence, or normality; those assumptions require engineering review. Minitab explains this sampling distinction in [Using subgroups to assess process capability](https://support.minitab.com/en-us/minitab/help-and-how-to/quality-and-process-improvement/capability-analysis/supporting-topics/data-and-data-assumptions/using-subgroups-to-assess-capability/).

### Variable Gage R&R: balanced one-way ANOVA

For `a` distinct parts, each with `r` repetitions, the model is `x_ij = mean + Part_i + error_ij`, with random part effects. Degrees of freedom are `a - 1` for Part, `a * (r - 1)` for Error, and `a * r - 1` for Total. The engine uses:

- `SS_Part = r * sum((mean_i - grand_mean)^2)`.
- `SS_Error = sum((x_ij - mean_i)^2)`.
- `MS = SS / DF`; `F = MS_Part / MS_Error` when its denominator is positive.
- `variance_repeatability = MS_Error`.
- `variance_part = max((MS_Part - MS_Error) / r, 0)`.
- `variance_total = variance_repeatability + variance_part`.

With one appraiser/system, `sigma_GRR = sqrt(MS_Error)` and reproducibility is not independently estimable. This is the no-operator one-way model described in Minitab's [method of analysis](https://support.minitab.com/en-us/minitab/help-and-how-to/quality-and-process-improvement/measurement-system-analysis/how-to/gage-study/crossed-gage-r-r-study/methods-and-formulas/method-of-analysis/). Negative estimated part variance is reported as zero with an explanation, following the nonnegative component convention in Minitab's [Gage R&R table formulas](https://support.minitab.com/en-us/minitab/help-and-how-to/quality-and-process-improvement/measurement-system-analysis/how-to/gage-study/crossed-gage-r-r-study/methods-and-formulas/gage-r-r-table/).

`StudyVar_GRR = k * sigma_GRR` (default `k = 6`), `%SV/Tol = 100 * StudyVar_GRR / (USL - LSL)`, and `%StudyVar = 100 * sigma_GRR / sigma_total`. A finite NDC is `max(1, floor(1.41 * sigma_part / sigma_GRR))`. NDC is N/A when the denominator is zero. Minitab explicitly describes [truncation and the minimum of one](https://support.minitab.com/en-us/minitab/help-and-how-to/quality-and-process-improvement/measurement-system-analysis/supporting-topics/gage-r-r-and-wheeler-s-emp-studies/using-the-number-of-distinct-categories-in-a-gage-r-r-study/).

The diagnostic R and Xbar charts use a separate range-based estimate, `sigma_chart = Rbar / d2(r)`, matching the supplied report. R limits are `Rbar * max(0, 1 - 3*d3/d2)` and `Rbar * (1 + 3*d3/d2)`; Xbar limits are `grand_mean +/- 3*sigma_chart/sqrt(r)`. These chart estimates do not replace the ANOVA variance components. Minitab distinguishes [Rbar and pooled standard deviation chart estimators](https://support.minitab.com/en-us/minitab/help-and-how-to/minitab-environment/settings-and-defaults/control-charts-and-quality-tools/estimating-standard-deviation/).

### Variable Gage R&R: balanced crossed ANOVA (two or more operators)

When two or more distinct Operators measured the same Test Item on the same tester and slot, they form one crossed study instead of separate one-way studies. Separating them would drop reproducibility and can pass a gage that the crossed study rejects: on a seeded synthetic study of 10 samples x 3 operators x 3 trials with operator offsets, the three separate one-way analyses gave %StudyVar of 25.5, 25.5 and 22.5 (NDC 5, 5, 6), whereas the crossed analysis gives %StudyVar 61.4, %Contribution 37.8, %SV/Tol 29.2 and NDC 1.

For `p` samples, `o` operators and `r` repetitions, the model is `x_ijk = mean + Sample_i + Operator_j + (Sample x Operator)_ij + error_ijk` with random effects, degrees of freedom `p-1`, `o-1`, `(p-1)(o-1)` and `p*o*(r-1)`. The interaction is tested as `F = MS_Int / MS_Error` and removed when its p-value is at least `interaction_alpha` (default 0.05, Minitab's default "alpha to remove interaction term"); the reduced model pools its sum of squares into error. Variance components are:

- With interaction: `repeat = MS_Error`, `int = max((MS_Int - MS_Error)/r, 0)`, `oper = max((MS_Oper - MS_Int)/(p*r), 0)`, `part = max((MS_Part - MS_Int)/(o*r), 0)`.
- Without interaction: `repeat = MS_Pooled = (SS_Int + SS_Error)/(df_Int + df_Error)`, `oper = max((MS_Oper - MS_Pooled)/(p*r), 0)`, `part = max((MS_Part - MS_Pooled)/(o*r), 0)`.
- `reproducibility = oper + int`, `GRR = repeat + reproducibility`, `total = GRR + part`. %Contribution, Study Var, %StudyVar, %SV/Tol and NDC then use the same definitions as above.

The full ANOVA table (with the interaction) is kept in the details and reports whenever the interaction was tested and removed. Operators who did not measure every sample, or unequal repetition counts, are rejected with an explanation rather than analyzed separately; map a fixture or nest to Slot or Tester if it should be evaluated and approved on its own (work instruction 8.7.2 also allows nests to stand in for operators in a crossed study, in which case map them to Operator). The R and Xbar charts have one point per sample/operator cell, and Measurement by Operator and Sample x Operator Interaction charts are added.

**Verification status.** The formulas follow Minitab's published [method of analysis](https://support.minitab.com/en-us/minitab/help-and-how-to/quality-and-process-improvement/measurement-system-analysis/how-to/gage-study/crossed-gage-r-r-study/methods-and-formulas/method-of-analysis/) and [Gage R&R table](https://support.minitab.com/en-us/minitab/help-and-how-to/quality-and-process-improvement/measurement-system-analysis/how-to/gage-study/crossed-gage-r-r-study/methods-and-formulas/gage-r-r-table/) pages. They are tested against a hand-calculated example and a separately written textbook calculation (interaction sum of squares by subtraction, closed-form F(2, d) p-value) on four datasets covering retained and removed interaction and truncated components. Minitab's help prints the full output of one crossed study, its "Gage data" example (10 parts x 3 operators x 3 readings, process tolerance 8, alpha to remove the interaction 0.05; data from Minitab's public data-set library). The engine reproduced all 64 figures printed for it to the last printed digit: both ANOVA tables, variance components with %Contribution, StdDev, Study Var (6 x SD), %Study Var, %Tolerance, the number of distinct categories and the interaction p-value (0.974). The interaction is removed in that example, so the retained-interaction path, one appraiser and unbalanced designs still have no Minitab reference. That comparison was run outside the automated suite, and the printed figures were transcribed from the help page by a page-reader tool, not checked by eye.

### Acceptance profiles

Each metric is displayed independently. Default percentage reference bands are `<10` PASS, `10` through `30` CONDITIONAL PASS, and `>30` FAIL. NDC is acceptable at 5 or greater. Only the explicitly selected decision metric determines the conclusion; metrics are not automatically combined.

**Customer criteria (development build; an optional layer, off by default).** Acceptance criteria sit on top of the statistics and never change a calculated value. In the Validation & Reports workspace no criteria are applied until the user chooses a customer (or a Cpk/Ppk limit for capability); without them the results and reports are statistics only. Minitab is the reference for the methods; the work instruction is background, and the presets below are only starting points taken from it. In the application, Gage R&R acceptance is chosen per customer through `AnalysisConfig.criteria`, a tuple of `Criterion(metric, enabled, pass_limit, fail_limit)` for %SV/Tol, %Study Var and NDC. For a percentage, PASS is below `pass_limit`, FAIL is above `fail_limit` and anything between is CONDITIONAL PASS; for NDC, PASS is at or above `pass_limit`, FAIL is below `fail_limit` and anything between is CONDITIONAL PASS. The overall result is the worst of the applied (`enabled`) metrics: any FAIL gives FAIL; otherwise an applied metric that cannot be evaluated gives N/A; otherwise any CONDITIONAL PASS gives CONDITIONAL PASS; otherwise PASS. Customers and their limits are edited in the Criteria dialog and stored in the user settings (`customer_criteria`, only entries that differ from the built-in presets). Built-in presets follow the supplied work instruction: SolarEdge and Zebra apply only %SV/Tol (8.6.1.1.2), SES applies NDC and %SV/Tol (8.6.1.1.3), and Jabil applies all three (8.6.1, table 8.12.2, 8.15.2). Keurig (8.6.1.1.4) and Hanwha (8.6.1.1.5) have rules that are not a per-metric worst-of (Keurig lets NDC decide only inside a %SV band), so they are left for the user to define. The work instruction is ambiguous at NDC = 4 (the label table says "> 4" for Pass and "< 4" for Fail; 8.6.1.1 says "lower than 5 is not appropriate"); the presets use 5. Without `criteria`, the earlier single decision-metric behaviour below is kept for programmatic use.

**Review flag.** The decision is never changed by another metric, but when the result is PASS or CONDITIONAL PASS and an informational metric (one that is not applied) would fail on its own limits, the result carries a warning, a **Review** column entry in the table and in the PDF/Excel summary, and a notice above the result table. This matters when a wide tolerance makes %SV/Tol small while the gage cannot tell the sampled parts apart: the supplied Meas Vin study has %SV/Tol 0.12 but %StudyVar 55.59 and a derived NDC of 2. The flag does not say the study is wrong; it says the %SV/Tol decision alone may be misleading.

The SolarEdge profile uses **only %SV/Tol** for the conclusion. %StudyVar and NDC are informational and cannot override it. This follows supplied work-instruction clauses 8.6.1.1.1 and 8.6.1.1.2 (PDF page 12; printed page 11). Clauses 8.6.1.2 and 8.6.1.3 (PDF page 13; printed page 12) define the strict 10% boundary. The older, separate `grr.py` pre-check used `<=10%`; the new statistical module applies the requested `<10%` boundary.

### Attribute Agreement Analysis (engine, ratings import, setup, result views, charts and PDF/Excel report)

`statistics/attribute.py`. One test item is one study: samples rated by one or more appraisers over repeated trials (Appraiser = the Operator field, Trial = the Trial field, Rating = the value, Standard = the new optional `Observation.standard`). Binary and multi-category nominal ratings are supported; every appraiser must rate every sample the same number of times. A usable Standard is the same on every rating of a sample and is given for every sample; a study may give none. A Standard that was given but is not usable (missing for some samples, or two different ones for a sample) does not stop the analysis: Within Appraisers is still computed, and only what depends on the Standard (Appraiser vs Standard, its kappa, the disagreement with it, All Appraisers vs Standard and the acceptance of vs Standard) is N/A, with the reason; the Checks call that Critical for the comparison with the Standard. No Standard at all is Info.

* **Percent agreement**, counted per sample: Within Appraisers (all of an appraiser's trials of the sample agree; needs two or more trials), Appraiser vs Standard (all equal the Standard), and, with two or more appraisers, Between Appraisers and All Appraisers vs Standard.
* **Confidence interval**: exact (Clopper-Pearson), alpha/2 on each side, except that with every sample matched the lower limit is alpha^(1/N) and the upper 1, and with none matched the lower is 0 and the upper 1-alpha^(1/N). Checked against Minitab's published limits: 30 of 30 = (90.50, 100.00) (the reference report), 50 of 50 = (94.18, 100.00), 47 of 50 = (83.45, 98.75), 37 of 50 = (59.66, 85.37) (Minitab's own example); a plain two-sided interval gives 88.43 for 30 of 30.
* **Fleiss' kappa** for each response and overall, with the standard error under H0 (Var(Kj) = 2/(n m (m-1)); overall: times ((sum pq)^2 - sum pq(q-p)) / (sum pq)^2), Z and the one-sided P value. With a known Standard, kappa is computed for each trial with the Standard as a second trial and averaged; the variance is the sum of the variances over (trials)^2. SE 0.105409 and Z 9.48683 of the reference report are what 30 samples rated 3 times give. All Appraisers vs Standard: the mean of the appraisers' kappas against the Standard, with the sum of their variances over (appraisers)^2.
* **Assessment Disagreement** (a known Standard and exactly two response levels), Minitab's table: each sample of an appraiser is counted once, as #X/Y when every trial is X and the Standard is Y (with Fail and Pass: #Pass/Fail a false pass, #Fail/Pass a false fail) or as #Mixed when its trials differ; Percent is 100 x count over the samples whose Standard is Y (over all samples for #Mixed), and N/A when no sample has that Standard. The columns are named after the responses. The single ratings that differ from the Standard over all ratings (100 x c / N, Minitab's methods page) stay in the result details. The rule follows Minitab's definitions and one published example; it has not been compared with a Minitab table and its raw data (`docs/attribute-minitab-comparison.md`).
* **Comparison with Minitab** (2026-11-01). Minitab's help page [Example of Attribute Agreement Analysis](https://support.minitab.com/minitab/help-and-how-to/quality-and-process-improvement/measurement-system-analysis/how-to/attribute-agreement-analysis/attribute-agreement-analysis/before-you-start/example) prints the whole output of a study with 4 appraisers, 2 trials, 50 samples, 5 ordered responses and a known Standard, and offers its worksheet (TextilePrintQuality). `tests/reference/` holds the worksheet and the tables as printed; `tests/test_attribute_minitab.py` compares 290 printed figures, each at the precision Minitab prints it, and all agree: counts, percent and 95 % interval of Within Appraisers, Each Appraiser vs Standard, Between Appraisers and All Appraisers vs Standard (50 figures), and Fleiss' kappa, SE, Z and P for every response and Overall in the four kappa blocks (240 figures), which covers the overall variance with five responses and the All Appraisers vs Standard kappa. The ratings are analysed as nominal categories, so the example's Kendall tables are not compared. The example has more than two responses, so it has no Assessment Disagreement table: nothing in it checks that table.
* **Acceptance** is a separate step: a minimum percent agreement (off by default) applied to Within and vs Standard each on its own. A measure that cannot be judged (no Standard, a single trial) is N/A, never PASS. The 90 % of the reference report is that report's own rule, not a Minitab threshold.

**Ratings import** (`statistics/ratings.py`, `ui/ratings_import.py`): a long-format CSV (comma, semicolon, tab or bar; UTF-8 or Windows-1252) or XLSX sheet with one row per assessment. The user maps the columns: Sample ID and Rating are required; Test Item (the file name when absent), Appraiser (blank: the one unnamed appraiser, shown as 1), Trial and Known Standard are optional. With no Trial column the ratings of each sample are numbered 1, 2, 3... in row order, which the import says; a Trial column is used as it is. The labels of the file are kept (PASS stays PASS, `Pass` stays `Pass`) unless the user maps a label to a category, which applies to the Rating and the Standard alike. Empty cells stay empty, so the engine reports them. The file is never changed. The Analysis tab offers the confidence level (90, 95 or 99 %, default 95) and acceptance (off by default; minimum agreement, default 90 %).

**Results, Details and Checks.** The results table is Test Item, Samples, Within %, vs Standard % and Kappa (the overall Fleiss' kappa Within Appraisers; the others are in the Details), with Acceptance Result added only when acceptance is on; a figure that is not available reads N/A, and the decimals follow the setting on screen. The summary reads `8 items analyzed · Acceptance off`, counts items that could not be analysed apart from acceptance, and never calls a computed result "not evaluated". The Details are tables, in the order of Minitab's report: Within Appraisers, Fleiss' Kappa Statistics, Each Appraiser vs Standard (with its kappa), Assessment Disagreement and, for two or more appraisers, Between Appraisers and All Appraisers vs Standard (each with its Fleiss' kappa). The Checks are Check | Finding | Status, for the selected item only: **Critical** (something cannot be calculated: a missing or duplicate Trial, a missing rating or Sample ID, an unbalanced study, which stop the whole item; or a Standard that is missing for some samples or differs within a sample, which stops only the comparison with the Standard), **Review** (a statistic is limited: an undefined kappa, one trial, a single response category) and **Info** (no Standard was given). Each finding is stated once.

**Charts and reports** (`stat_charts.agreement_charts`, `stat_reports.attribute_tables`). The Assessment Agreement graph is two panels drawn by the existing chart renderer, on screen and in the PDF: Within Appraisers and Appraiser vs Standard. Each shows the percent agreement of every appraiser as a circle and its exact confidence interval, at the confidence level of the analysis, as two X markers joined by a line (30 of 30 reads 100.00 %, (90.50, 100.00)). The percent scale ends at 100 and starts at the lower ten that holds the lowest limit, with room for the markers at 0 and 100. A panel the study cannot have (one trial, no Standard) is left out; a Standard that was given but cannot be used leaves its panel with an N/A and the reason. No histogram, R chart or Xbar chart applies. The PDF prints, in Minitab's order: the study information, Within Appraisers (assessment agreement, Fleiss' kappa), Each Appraiser vs Standard (assessment agreement, Fleiss' kappa), Assessment Disagreement and, for two or more appraisers, Between Appraisers and All Appraisers vs Standard (each with its Fleiss' kappa), and then the graph on a page of its own; the workbook has the same tables with every figure in full (an interval is a lower and an upper cell), the two charts as native Excel charts, and, if asked, the ratings. Acceptance, when a minimum agreement was applied, is a separate table that says it is a criterion of the user and not a statistical result. The screen, the PDF and the workbook are made from the same result snapshot, and a test compares them cell by cell. Assessment Disagreement is the same seven-column table on screen, in the PDF and in the workbook (Appraiser, #Pass/Fail, Percent, #Fail/Pass, Percent, #Mixed, Percent), and is left out without a known Standard.

Attribute Agreement is not run from the window until its views have been seen working there: `ATTRIBUTE_RESULTS_READY` and `ATTRIBUTE_REPORTS_READY` in `ui/validation_workspace.py` stay False. To check them before they are released, set `DATAMAPPERX_ATTRIBUTE_RESULTS=1` (allows running it) and `DATAMAPPERX_ATTRIBUTE_REPORTS=1` (allows its PDF and Excel report); `docs/attribute-gui-verification.md` is the checklist.

Not verified, or not calculated: the **Assessment Disagreement** counting rule and divisors were not compared with a Minitab table that comes with its raw data. Minitab's help ([Assessment disagreement](https://support.minitab.com/en-us/minitab/help-and-how-to/quality-and-process-improvement/measurement-system-analysis/how-to/attribute-agreement-analysis/attribute-agreement-analysis/interpret-the-results/all-statistics-and-graphs/assessment-disagreement/), [methods and formulas](https://support.minitab.com/en-us/minitab/help-and-how-to/quality-and-process-improvement/measurement-system-analysis/how-to/attribute-agreement-analysis/attribute-agreement-analysis/methods-and-formulas/assessment-disagreement/)) defines the three counts in words and gives one percent, 100 x c / N, but not what each Percent column is divided by. One published example (*Six Sigma Case Studies with Minitab*, chapter 12, as quoted: 10 samples, #Pass/Fail 1 = 25.00, #Mixed 1 = 10.00) is consistent with the divisors used, but its data could not be read; the divisor of #Fail/Pass (by symmetry), a percent with nothing to divide by (N/A), one trial per sample and responses other than Pass and Fail are unverified. Nine controlled studies to run in Minitab are in `docs/attribute-minitab-comparison.md`. Ordered categories (Kendall's coefficients) and Cohen's kappa are out of scope. The method stays at "Pending Minitab Verification" until the disagreement table has been compared with Minitab output.

### Data checks (screening aids, not verified against Minitab)

The Checks tab of the Results shows a few plain statements per test item. They change no figure, block nothing and are not printed in the report. Thresholds follow Minitab's Assistant white papers for Gage R&R (Crossed) and Capability Analysis and its help on measurement-system acceptance; the wording is ours. For a capability item the tab shows only what was found, one short line per check (`Check.brief`; the full statement stays in `Check.message`), and a sequence test on readings whose order is not verified is a note, not a warning. Code: `datamapperx/statistics/checks.py`; tests: `tests/test_checks.py`.

- **Variable Gage R&R, amount of data.** Parts: fewer than 10 (look), 10 to 15 (the usual minimum, still imprecise), more than 15 and fewer than 35 (well above the minimum), 35 or more (enough). Minitab's simulations (10 parts, 3 operators, 2 replicates) give a 90 % interval of about 0.61 to 1.37 for the ratio of the estimated to the true part-to-part standard deviation; about 35 parts give a margin of 20 % and about 135 give 10 %. Operators: one appraiser (repeatability only); two or fewer, or fewer than 10 parts (a general tendency, not a precise figure); three to five (reproducibility less precise); more than five.
- **Guidelines** (AIAG, as Minitab quotes them): %Study Var and %Tolerance below 10 %, 10 % to 30 %, above 30 %; %Contribution below 1 %, 1 % to 9 %, above 9 %; at least 5 distinct categories. Shown as guidance, never as PASS or FAIL.
- **Capability, amount of data:** at least 100 observations.
- **Capability, stability** (individual readings only): I chart with limits mean +/- 3 MRbar/d2 (d2 = 1.128); test 1 (a reading more than 3 sigma from the centre line) and test 2 (9 or more readings in a row on one side of the centre line); MR chart with upper limit MRbar (1 + 3 d3/d2), d3 = 0.8525, test 1. The order of the readings matters: unless it is known (File time order, assigned timestamps or confirmed), the check says so. Subgroup analyses are not assessed here (Minitab's Assistant uses Xbar and S charts with tests 1, 2 and 7).
- **Capability, normality:** Anderson-Darling with the mean and standard deviation estimated from the data, A'^2 = A^2 (1 + 0.75/n + 2.25/n^2), and the p-value from the piecewise equations of D'Agostino and Stephens (1986), whose coefficients Minitab prints in its Normality Test methods. p below 0.05 is flagged; at least 8 readings are needed. The A^2 formula and the correction factor appear on Minitab's page only as images, so the standard forms were used. The implementation was compared with scipy (A^2) and statsmodels (p) on 200 samples, with differences below 3e-12, but not with Minitab output. Box-Cox and Johnson transformations are not implemented.

## Automated comparison and scope

`tests/test_stat_reference.py` performs optional local comparisons against the five FT items when the confidential raw folder is available. It skips with an explicit reason in a clean checkout rather than distributing company raw measurements. `DATAMAPPERX_REFERENCE_LOGS` can point to the same study in a different folder. Independent aggregate golden checks use configurable `DATAMAPPERX_REFERENCE_ABS_TOL` and `DATAMAPPERX_REFERENCE_REL_TOL`; printed-report checks use half the last displayed unit. Assertion output includes actual values, expected values and differences.

The remaining statistical tests use redistributable synthetic data and run without the reference PDFs or proprietary logfiles. UI/report tests verify that display and exports consume the same result objects; raw measurement values are not changed for report generation. The final test run and counts are recorded in the implementation handoff.

Unsupported designs include nested multi-appraiser studies, unbalanced GRR (crossed or one-way), one-sided tolerance for %SV/Tol, historical process sigma, nonnormal transformations, attribute GRR, confidence intervals and misclassification probabilities. Each tester and slot remains a separate study. Operators of the same tester and slot are analyzed together as a crossed study; one-system estimates of different testers or slots must not be represented as a pooled reproducibility estimate. Two-sided tolerance is required for GRR %SV/Tol. The existing desktop Tk application is a Windows desktop application, not a mobile website.

## Implementation map and verification

- `datamapperx/statistics/`: `Dataset`, `Study`, study design, the RawData.xlsx importer, pure normalized observation models, mapping, validation, numeric primitives, capability, one-way and crossed ANOVA, acceptance profiles and review flags, shared formula explanations and calculation details.
- `datamapperx/ui/validation_workspace.py`: the Validation & Reports workspace (Data, Analysis, Results, Report). It builds an immutable `Dataset` from the Data Mapping scan or a RawData.xlsx, keeps the settings in a `Study`, runs the statistics on a background task from a captured `StatisticsPlan`, judges them with the customer criteria (`Study.evaluate`) and marks results stale when anything the numbers depend on changed. `datamapperx/ui/validation.py` holds its dialogs (file assignments, customer criteria, analysis conditions).
- `datamapperx/ui/main_window.py`: adds the Validation & Reports workspace beside Data Mapping while preserving selection, duplicate mapping, preview, quick pre-check, limits and raw Excel export. Data Mapping tells the workspace when its data changed (a counter, so an in-place change of a duplicate choice is seen); the workspace never writes to it.
- `datamapperx/stat_charts.py` and `datamapperx/stat_reports.py`: shared chart geometry and PDF/Excel reports modelled on Minitab's Gage R&R and Process Capability reports (ANOVA, Variance Components, Gage Evaluation, NDC and the Gage R&R graphs; Process Data, Overall and Potential (Within) Capability, Performance (PPM) and the histogram). - `tests/test_statistics.py`, `tests/test_stat_reference.py`, `tests/test_stat_reports.py`, and additional cases in `tests/test_ui.py`: independent known-data calculations, edge cases, actual reference studies, formula/report consistency, optional workflow, mapping identity, order, filtering, export, stale background answers and desktop geometry.
- `requirements.txt`, `pyproject.toml`, `DataMapperX.spec`: add ReportLab and retain its runtime resources/Pillow in packaged applications. No executable release was published.

## Report runtime repair

The open source application used `DataMapperX-ui-venv`, which did not have ReportLab installed; earlier verification had supplied it through a separate test dependency directory. This caused `No module named 'reportlab'` at PDF export. The declared runtime dependencies were installed in the actual launch environment, and full capability/GRR PDF and Excel reports were generated successfully there with no test PYTHONPATH.

`tools/build.ps1` now checks the runtime dependencies before packaging. `datamapperx/selftest.py` generates and validates all four full statistical reports during the executable smoke test, so opening the application alone can no longer pass the build while PDF support is missing. Two regression tests cover successful report generation and missing ReportLab. The 25 targeted report/release/startup checks and Ruff passed.

The local `dist/DataMapperX.exe` was rebuilt with ReportLab and its dependencies. Its packaged smoke test passed, including capability and GRR PDF/Excel generation, scanning, raw export and the desktop workflow. The preceding executable is retained under the ignored `tmp/stat-runtime-backup/` directory. No release was published.
